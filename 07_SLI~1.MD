# Why Product + Organization slicers return blank

**Short answer: there is no circular dependency, and the model is not broken.**
You have selected a product and a plant that never occur together, so the
intersection is genuinely empty and every measure correctly returns blank.

---

## 1. The model has no circularity

I checked the relationship graph you were given:

- 11 tables, 10 active relationships
- **no cycles**
- **exactly one filter path** from every dimension to every fact

```
dim_Product ─┐
dim_Organization ─┤
dim_Customer ─┼──> dim_SalesOrderLine ──> fact_Invoice
dim_Currency ─┤                       ──> fact_SalesOrder
dim_ReturnReason ─┘                   ──> fact_Shipment
```

Power BI would refuse to create a circular set of active relationships, and it
would warn you about ambiguity. If you saw neither, you do not have either
problem.

---

## 2. What is actually happening

`ProductKey` and `OrgKey` are **not independent**. Both are built from the same
underlying column:

```
ProductKey = Line_Inventory_Item_Id       + '.' + Line_Ship_From_Inventory_Org_Id
OrgKey     = Data_Source_Region           + '-' + Line_Ship_From_Inventory_Org_Id
                                                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

Measured on your v2 extract:

| | |
|---|---|
| Distinct products | 1,726 |
| Distinct organizations | 70 |
| Possible combinations | 120,820 |
| Combinations that actually exist | **1,726** |
| Grid populated | **1.43%** |
| Products belonging to more than one org | **0** |

Every product belongs to **exactly one** organization. So of the 120,820
combinations your two slicers let a user pick, only 1,726 return anything —
**98.6% of selections are guaranteed blank.**

Example from your data: `348436.7572` exists only under `EUR-7572`. Pick that
product with any of the other 69 organizations and the result is empty.

### Why the slicers let you do it

The two slicers sit on **different dimension tables**. With Single-direction
filtering — which is correct and should not be changed — a slicer on
`dim_Product` filters the bridge, but it does **not** filter `dim_Organization`.
So the Organization slicer keeps showing all 70 values even after you have
chosen a product, and nothing stops you selecting an impossible pair.

---

## 3. Confirm it in 30 seconds

Drop this measure on the page with both slicers active:

```dax
Slicer Diagnostic =
VAR LinesInScope   = COUNTROWS( dim_SalesOrderLine )
VAR ProductsPicked = COUNTROWS( VALUES( dim_Product[ProductKey] ) )
VAR OrgsPicked     = COUNTROWS( VALUES( dim_Organization[OrgKey] ) )
RETURN
    IF(
        ISBLANK( LinesInScope ),
        "No order lines match this combination — "
            & ProductsPicked & " product(s) x " & OrgsPicked
            & " org(s) never occur together",
        FORMAT( LinesInScope, "#,0" ) & " order lines in scope"
    )
```

If it reports **"No order lines match"**, the model is fine and the selection is
the problem. If it reports a line count but `Revenue USD` is still blank, the
cause is something else — see section 6.

---

## 4. The fix — slice from one table

Two slicers on the **same** table cross-filter each other natively. Since every
product belongs to exactly one organization, put the organization attributes
onto `dim_Product` and slice from there. Selecting a region then narrows the
plant list, which narrows the product list, and no impossible combination is
ever offered.

### Option A — patch QUERY 6 in `06A_SQL_AllObjects.sql`

```sql
SELECT p.ProductKey, p.Item_Id, p.Item_Number, p.Product_Description,
       p.Inventory_Org_Id,
       p.Region, p.Operating_Unit, p.OrgKey        -- added
FROM (
    SELECT
        CONCAT(sofv.[Line_Inventory_Item_Id], '.',
               sofv.[Line_Ship_From_Inventory_Org_Id])      AS ProductKey,
        sofv.[Line_Inventory_Item_Id]                       AS Item_Id,
        sofv.[Line_Product_Item_Number]                     AS Item_Number,
        sofv.[Line_Product_Item_Description]                AS Product_Description,
        sofv.[Line_Ship_From_Inventory_Org_Id]              AS Inventory_Org_Id,
        sofv.[Data_Source_Region]                           AS Region,
        sofv.[Operating_Unit_Name]                          AS Operating_Unit,
        CONCAT(sofv.[Data_Source_Region], '-',
               sofv.[Line_Ship_From_Inventory_Org_Id])      AS OrgKey,
        ROW_NUMBER() OVER (PARTITION BY CONCAT(sofv.[Line_Inventory_Item_Id], '.',
                                               sofv.[Line_Ship_From_Inventory_Org_Id])
                           ORDER BY sofv.[Ordered_Date] DESC) AS rn
    FROM cml.[Sales_Order_F_V] AS sofv
    WHERE sofv.[Line_Inventory_Item_Id] IS NOT NULL
      AND sofv.[Line_Cancelled_Flag] = 'N'
      AND (
              sofv.[Line_Schedule_Ship_Date]   >= '2026-01-01'
           OR sofv.[Line_Actual_Shipment_Date] >= '2026-01-01'
          )
) AS p
WHERE p.rn = 1
UNION ALL
SELECT '-1', NULL, 'Unknown', 'Unknown', NULL, 'Unknown', 'Unknown', '-1'
```

### Option B — patch query 16 in `02B_PowerQuery_ThreeQueries.m`

```m
    Picked = Table.SelectColumns(Source, {
        "ProductKey", "Item_Id", "Item_Number", "Product_Description",
        "Inventory_Org_Id", "Region", "Operating_Unit", "OrgKey",   // added
        "Ordered_Date"}),
```

…and add matching values to the Unknown row.

### Then build one hierarchy

On `dim_Product`, create a hierarchy: **Region → Operating_Unit →
Product_Description**. Put a single hierarchy slicer on the page, or three
slicers all sourced from `dim_Product`. They will cascade correctly because they
are on one table.

Keep `dim_Organization` in the model — it is still the right dimension for
"revenue by plant" when no product is in play.

---

## 5. If you would rather keep two separate slicers

Set the Organization slicer to hide values that have no data:

**Format pane → Slicer settings → Options → "Show items with no data" = Off**
is the default, but it only suppresses values with no data *in the current
filter context*, which requires the two dimensions to filter each other.

The only way to make them filter each other is **bidirectional cross-filtering
on `dim_Product` → `dim_SalesOrderLine`**. I do not recommend it here:

- it creates a second filter path into all three facts
- Power BI will start reporting ambiguity as soon as another bidirectional
  relationship is added
- the `Fan Out Alert` measure will not catch it, because it is not a fan-out

Putting the attributes on one table achieves the same result with none of that.

---

## 6. If the diagnostic shows lines in scope but the measure is still blank

Then it is not the slicer combination. Check in this order:

1. **Relationship direction.** `dim_Product` must be the **1** side and
   `dim_SalesOrderLine` the **many** side. If it was created the other way
   round, filters will not reach the facts.
2. **Key data types.** `ProductKey` and `OrgKey` must be **Text** on both sides.
   A Text-to-Whole-Number relationship is accepted by Power BI and matches
   nothing.
3. **Cross-filter direction.** Should read Single on all twelve relationships.
4. **`Revenue USD` lives on `fact_Invoice`.** Confirm
   `dim_SalesOrderLine → fact_Invoice` on `LineKey` is **active** — the chain is
   two hops, and a broken second hop looks identical to a broken first hop.
5. **Run `Unresolved Rate Lines` and `Orphan Shipment Rows`.** Both should be
   zero. Anything else means keys are not matching.

---

## 7. Worth knowing regardless

`dim_Organization` is, strictly, a **parent of `dim_Product`** rather than a
peer of it — every product rolls up to exactly one organization. Modelling it as
a snowflake (`dim_Product → dim_Organization`) would express that honestly and
make the cascade automatic. I kept them as siblings because it keeps every
dimension one hop from the bridge, which is simpler to reason about and faster.
Adding the org columns to `dim_Product`, as in section 4, gets the usability
benefit without changing the model shape.
